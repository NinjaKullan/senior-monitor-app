# Spec 019 — Ask Kettle from an assistant (read-only MCP)

Status: RATIFIED by Hema, 2026-09-05 (DECISIONS 284); strings verbatim.
Builds on 013 (email code sign-in), 015 (circles), 017 (pause), 018
(notes), the outbound ledger (007) and the template registry.

## 1. What this is

A child asks the assistant they already use ("how's Mom today?") and
gets Kettle's own sentence back. Kettle becomes one more connector in
the Claude app, the way Gmail is: connect once, then just ask. Nothing
is written through this door in v1. Parents are never involved.

The sibling sentence (264): "Kettle shows up in your Claude app the
way Gmail does; you sign in once with the code, then you just ask."

## 2. Rulings (founder, Sep 5)

- Two moments, opposite needs. CONNECTING is a one-time seated act,
  about a minute, eyes and two thumbs. ASKING is forever and needs
  nothing: no app switch, no code, no thinking. All the ease we build
  goes into asking; connecting only has to be painless once.
- Sign-in is OAuth on top of the existing email-code sign-in. No
  tokens to copy, no new credential. The sheet the assistant opens is
  Kettle's normal login, then one consent screen, then Allow.
- Privacy in public is the person's call. If they ask for Mom's
  status in a cafe or a car, Kettle answers. No "are you somewhere
  private" gate, no read-aloud restriction, no extra confirmation.
- Answers are one to three of Kettle's sentences, because they may be
  read aloud. What-never-how, no counts, no verdicts (copy laws).
  Tools take names ("Amma"), never ids.
- Two doors, one mechanism: the assistant's own Connectors screen is
  canonical; Kettle's Family screen explains it and lists what is
  connected. Disconnect works from either side.
- One truth: the assistant reads the ledger, it does not judge. What
  Kettle already said today is the answer; the engine stays the only
  thing that decides what a day means.

## 3. How it works (the plumbing, in one paragraph)

kettle-api is both the MCP server and the authorization server, on its
existing public host. An assistant added by URL discovers the auth
server from a 401 with a WWW-Authenticate header, registers itself
(dynamic client registration), and sends the person to /oauth/
authorize with a PKCE challenge. Kettle stores that request and sends
the person to the webapp's /connect page, which signs them in if they
are not (013) and shows the consent screen (§6). Allow posts the
approval to kettle-api with the person's Supabase session; Kettle
mints a one-time code and sends the person back to the assistant. The
assistant swaps the code for tokens at /oauth/token. From then on
every tool call carries a bearer token that resolves to exactly one
person, and that person sees exactly the circles the app would show
them, checked at call time.

## 4. Auth server (Claude's documented requirements, Sep 2026)

- Endpoints on kettle-api: `/.well-known/oauth-protected-resource`
  (resource = the exact MCP URL, `https://<api host>/mcp`;
  authorization_servers = [api host]; scopes_supported =
  ["kettle:read"]), `/.well-known/oauth-authorization-server` (RFC
  8414; code_challenge_methods_supported = ["S256"];
  registration_endpoint; grant_types authorization_code and
  refresh_token; token_endpoint_auth_methods_supported includes
  "none"), `/oauth/register` (RFC 7591, JSON), `/oauth/authorize`,
  `/oauth/token` (form-urlencoded), `/oauth/approve` (Kettle's own,
  called by the webapp), `/mcp` (Streamable HTTP; official `mcp`
  Python SDK mounted in the FastAPI app).
- `/mcp` without a valid bearer returns 401 with
  `WWW-Authenticate: Bearer resource_metadata="https://<api host>/.well-known/oauth-protected-resource"`.
  A 401, never a tool error.
- Redirect URIs: the ones the client registered, matched exactly,
  except loopback (`http://localhost/...` and `http://127.0.0.1/...`)
  where the port is ignored (Claude Code). Claude's hosted surfaces
  use `https://claude.ai/api/mcp/auth_callback`.
- PKCE S256 required on every authorize; a request without it is
  refused. `state` echoed back.
- Codes: single use, ten minutes. Access tokens: opaque, one hour.
  Refresh tokens: rotated on every use; the old one dies in the same
  response the new one is issued. A grant unused for ninety days is
  expired; its refresh fails with `invalid_grant` and the assistant
  reconnects. Tokens are stored hashed (sha256), never plain.
- Discovery, register and token must answer well under ten seconds;
  no upstream calls inside them.
- Client name: the `client_name` the assistant registered, else
  ASSISTANT_FALLBACK. Shown on the consent screen and in Family.
- `/oauth/approve` takes the pending request id and the person's
  Supabase access token (Authorization: Bearer). kettle-api verifies
  it against the project's JWKS (kettle-prod signs with an ECC P-256
  key, checked Sep 5; the JWKS URL is
  `https://<project ref>.supabase.co/auth/v1/.well-known/jwks.json`,
  from a new env `SUPABASE_JWKS_URL`; cache it, refetch on an unknown
  kid) and takes `sub` as auth_user_id. No shared secret is needed. CORS for this one route is locked
  to the webapp origin, the same pattern as the waitlist route.

## 5. Data

Migration numbered at build time.

- `assistant_requests`: id, client_id, client_name, redirect_uri,
  code_challenge, state, scope, created_utc, expires_utc,
  auth_user_id null, code_hash null, used_utc null. Pending
  authorizations; swept after an hour.
- `assistant_clients`: client_id, client_name, redirect_uris,
  created_utc. From /oauth/register.
- `assistant_grants`: id, auth_user_id, client_id, client_name,
  created_utc, last_used_utc, revoked_utc, access_token_hash,
  access_expires_utc, refresh_token_hash, refresh_expires_utc.
  One row per connection a person made. The Family screen reads a
  person's own rows through RLS (`auth_user_id = auth.uid()`);
  columns with hashes are not selectable by `authenticated` (view or
  column grants). Nothing on these tables is writable by the client;
  0004 doctrine.
- Function `app_revoke_assistant(grant_id)` (SECURITY DEFINER,
  `authenticated` only): sets revoked_utc on the caller's own grant.
  A revoked grant's access token and refresh token both fail from
  the next call.
- What a token resolves to: auth_user_id, then the members rows for
  that user (the same set `app_current_family_ids()` yields), at
  call time. Removing someone from a circle (015) removes it from
  their assistant in the same instant. No family id is stored on the
  grant.

## 6. Webapp

- `/connect?request=<id>`: if not signed in, the 013 login, then back
  here. Shows CONNECT_TITLE, CONNECT_BODY with the client name and
  the parents' names across every circle the person is in
  ("Amma and Appa"; "Amma, Appa and Mom" across circles),
  CONNECT_READ_ONLY, then CONNECT_ALLOW and CONNECT_CANCEL. Allow
  posts to /oauth/approve and follows the returned redirect. Cancel
  redirects with `error=access_denied`. Expired or unknown request:
  CONNECT_EXPIRED and a link back to Today.
- Family screen, new section ASSISTANTS_SECTION below the circle:
  ASSISTANTS_INTRO, then the MCP URL with ASSISTANTS_COPY, then the
  person's own connections as "{client} · since {date}" with
  ASSISTANTS_DISCONNECT (confirm ASSISTANTS_DISCONNECT_CONFIRM,
  ASSISTANTS_DISCONNECT_YES, ASSISTANTS_DISCONNECT_NO). Empty state:
  ASSISTANTS_NONE. Dates in the viewer's zone (279).
- Nothing else in the app changes.

## 7. Tools (all read-only; every answer is sentences, not fields)

Names are looked up case-insensitively against `parents.display_name`
across the person's circles. No match: NO_SUCH_PARENT listing the
names they can ask about. Two circles with the same name: both,
each prefixed with the circle name. No parent given: every parent
they can see, one paragraph each, prefixed with the name.

1. `today(parent?)`: for each parent, in order: the pause line if
   paused (017 PAUSED_CARD / PAUSED_UNTIL / PAUSED_OPEN_ENDED); else
   the latest note Kettle sent today (the rendered text of the last
   `sent_messages` row with status sent for that parent's local day,
   through `outbound_templates.render`), else TODAY_NOTHING_YET; then
   the heard line (HEARD_* from copy, computed from the last ping);
   then, if the person is in a different zone, CITY_NOW for the
   parent. Demo circle rows (families.demo) answer the same way; the
   ledger is real for them.
2. `parent_day(parent, date?)`: `date` is YYYY-MM-DD in the parent's
   zone, default today, at most sixty days back. Every sent note
   that day in ledger order, rendered, each prefixed by its kind in
   plain words (MORNING_NOTE, EVENING_NOTE, ASK_SENT, FOLLOW_ON_SENT,
   ALL_CLEAR_SENT), plus DAY_NOTHING if none. Withheld and skipped
   rows are not shown; the family never received them (render_
   digest's rule).
3. `memory(parent?, since?)`: family notes and their replies (016),
   newest first, at most forty; each as "{date} · {author}: {text}"
   with EDITED_MARK where set, replies indented one level; upcoming
   dated notes first under UPCOMING_LABEL. `parent` filters by tag;
   `since` is YYYY-MM-DD. Dates in the family's zone, said once in
   the tool description. Kettle's own lines carry AUTO_NOTE_AUTHOR.
4. `who_to_call(parent?)`: the parent's phone (CALL_LABEL form, with
   the number), then the circle's contacts (0021) as "{name} · {phone}
   · {note}". This is the only tool that returns a phone number.
5. `circles()`: each circle the person is in: name, the parents with
   city and CITY_NOW, the members as "{name} ({role})". No emails.

Tool descriptions (the text the assistant reads) are strings too
(§8) and follow the copy laws. A tool never raises to the assistant
for an expected case; it answers in a sentence.

## 11. Out of scope

Writing anything (notes, pause) through the assistant in this build.
Adding a note by voice is the founder's first candidate for an
amendment once "how's Amma" works from a phone: one tool `add_note`,
one consent line, the assistant asks before it runs, and the note
carries an "added by {name} via {client}" mark so typed and dictated
words are told apart. Discussed Sep 5, not ruled; the Claude
connector directory listing; ChatGPT and others (same standard; they
come when someone asks); a Kettle voice of its own; any gate on where
or how a person asks (ruled out, §2).

## Amendment A (2026-09-08): notes and replies through the assistant

Status: RATIFIED by Hema, 2026-09-08 (DECISIONS 311 rulings; 316 for
this text); strings verbatim. Builds on 016 (replies), 018 (notes,
author_member_id) and this spec's door. Pause stays in the app.

### A.1 What this adds

Two write tools behind the same door: a person tells their assistant
"tell Kettle Amma's doctor visit is Thursday" or "reply to Priya: I'll
call her tonight", the assistant reads it back and asks, and the words
land in the family's Memory marked as dictated. Nothing else is written
through the door. Notes and replies are journal content and never an
input to what a day means; any future tool that changes Kettle's
behaviour (pause, thresholds) is a different class with its own ruling.

### A.2 Scope and consent

- A second scope, `kettle:write`. Discovery lists both scopes; a grant
  stores the scope it was given. Every existing grant is `kettle:read`
  and stays so: the write tools answer NEED_WRITE until the person
  connects again and sees the consent screen say what can be written.
- The consent screen with `kettle:write` requested: CONNECT_TITLE,
  CONNECT_BODY_WRITE (client, names), CONNECT_WRITE_NOTE, then Allow
  and Not now as today. A read-only request keeps CONNECT_BODY and
  CONNECT_READ_ONLY unchanged.
- The Family screen's connection row shows ASSISTANTS_SINCE_WRITE for a
  write grant ("{client} · since {date} · can add notes"),
  ASSISTANTS_SINCE for a read one. Disconnect unchanged.
- The write tools carry `readOnlyHint: false` (`destructiveHint: false`,
  `idempotentHint: false`), which is what makes the assistant ask
  before each one. Their descriptions tell the assistant to read the
  words back first (§A.6).
- The server's `instructions` become SERVER_INSTRUCTIONS (§A.6), so an
  assistant asked to pause a parent sends the person to the app
  instead of improvising.

### A.3 Tools

Names and dates, never ids (§2). Each answers in a sentence; no
expected case raises.

1. `add_note(text, parent?, date?)`: a note in the family's Memory.
   `parent` (a name, matched as `today` matches) tags the note and
   picks the circle; with no parent, a person in exactly one circle
   writes to it, and a person in several is answered WHICH_PARENT and
   nothing is written. `date` is YYYY-MM-DD in the family's zone and
   becomes `event_date` (an upcoming note, 016). Body cap is the
   table's (2000); over it, CANNOT_SAVE. Answer: NOTE_SAVED.
2. `reply(text, author?, date?)`: a reply under a note. The target is
   the newest note (kind note, not a reply, not deleted) in the
   person's circles; `author` narrows to that person's notes (matched
   against the note's member display name, then its author label,
   case-insensitively); `date` narrows to notes written that day. No
   match: NO_NOTE_TO_ANSWER and nothing written. The 016 rules hold
   (no reply to a reply, none to Kettle's own lines). Answer:
   REPLY_SAVED with the note's author and date.

The PM's one departure from 311: `author` is optional. Notes written
before 018 carry the label "Family" and no member, so a required author
would miss them; "reply to the latest note" is also how people speak.

### A.4 The mark and the limit

- Migration numbered at build time (0032 next free): `journal_entries.via_client
  text null`. A dictated note or reply carries the client's name there;
  `author_member_id` is the person, `author_label` their display name,
  as a typed note would carry. The webapp and the server render the
  author of such a line as AUTHOR_VIA ("{name} via {client}") wherever
  an author is shown (Memory, the `memory` tool, the digest's note
  lines if any). Edit and Delete work on it as on any note of theirs.
- Twenty writes an hour per grant, counted from the table (rows with
  this person's `author_member_id` and a non-null `via_client` in the
  last hour); over it, WRITE_LIMIT and nothing written. No alert.
- Every write is the person's own words: the body is not scanned by
  the copy laws (the journal rule, 285 f); the chrome around it is.
- Nothing about the assistant's request beyond the body, the mark and
  the target is stored.

### A.5 Data and auth

- `assistant_grants.scope` (exists) decides; `/oauth/authorize` accepts
  `kettle:read`, `kettle:write` or both; `kettle:write` implies read.
  A write tool on a read grant answers NEED_WRITE, never a 401 (the
  grant is valid; it is narrow).
- Writes run server-side as the service role on behalf of the resolved
  member (auth_user_id → members row in the target family, checked at
  call time as reads are); a person removed from a circle cannot write
  to it in the same instant.
- `/oauth/approve` records the requested scope on the grant; the
  consent screen reads it from `/oauth/pending`.

### A.7 Tests (CC)
